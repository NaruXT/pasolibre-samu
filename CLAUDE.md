## Intent Layer

**Before starting any of the 11 tracer-bullet tickets in the GitHub issue tracker, read this section first** — the codebase itself is still just the default `create-next-app` scaffold, so these decisions aren't visible anywhere else yet.

**Before modifying code under `lib/`, read `lib/AGENTS.md` first** — it covers the domain-logic/I-O-boundary layer (tick orchestration, Portal, Mapbox, TomTom, semáforo/hospital datasets) in more detail than fits here.

`app/`, `components/`, and `docs/` are all still under the 20k-token threshold — no dedicated node needed for them. `lib/` crossed it (42.1k tokens as of 2026-08-08) and got its own node; re-run `scripts/estimate_tokens.sh` from the `intent-layer` skill periodically as more feature code lands to check whether another directory needs one too. Note: `lib/`'s token count is skewed by two large static OSM datasets (`lib/semaforo/semaforosSanBorjaYColindantes.ts`, `lib/hospital/hospitalesSanBorjaYColindantes.ts`) — bulk data, not logic complexity.

### Global Invariants

- **One Next.js project, no separate service.** The sequencing agent lives in a Next.js API route — never split it into a Python service or a second deployable.
- **Single orchestration seam.** All tick logic (ETA calc → cycle phase calc → TomTom congestion lookup → LLM call → Portal publish) funnels through one API route. Tests exercise that route as a unit; only the I/O boundaries (TomTom, the LLM call, the Portal REST call) are replaced with test doubles — ETA and cycle-phase calculations are pure functions and must run for real in tests.
- **The agent decides once per semáforo per trayecto.** Invoke the LLM only when a semáforo's ETA enters the decision window (~60s) and no decision has been published for it yet in this trip. Never re-invoke on later ticks for an already-decided semáforo.
- **Semáforo cycle phase is a pure function of `(semaforoId, elapsedTime)`.** 90s cycle, 45s green / 45s red, per-semáforo offset derived deterministically from `semaforoId` via `lib/semaforo/fase.ts#offsetDeSemaforo` — never `Math.random()`, never state stored separately from that derivation. **The hash needs an avalanche finalizer, not just a charCode sum** (ticket #9): short sequential real IDs like OSM node ids differing by 1 produced near-identical offsets under a naive sum-mod-90 hash, visually syncing semáforos that should look independent. Fixed with a djb2 accumulation + MurmurHash3-style finalizer; see the comment there before touching this function again.
- **Intersection cross-protection (2026-08-09): forcing a semáforo to green also forces its geographic neighbors to red.** Real bug reported by the user with a screenshot: two real OSM traffic-signal nodes a few meters apart (different approaches of the same physical intersection, e.g. Salaverry Ave / Av. Rebagliati) both showed green at once — each semáforo's phase and LLM decision are fully independent (see the pure-function invariant above), with nothing modeling that two nodes might share an intersection, so cross traffic could show green at the same moment as the ambulance. The semáforo dataset (ticket #9) never verified which street crosses at each node (explicitly out of scope, see below) — no real street-topology data exists to detect this properly. Fixed with a geographic proxy instead: `lib/semaforo/semaforosVecinos.ts#semaforosVecinos` treats any two semáforos within `RADIO_INTERSECCION_METROS` (50m) as the same physical intersection — calibrated by measuring a real 4-node intersection in the dataset (Salaverry/Rebagliati cluster: nodes 18-46m apart), with headroom below Lima's arterial block length (~80-150m) so it doesn't reach into the next block. `orquestarTick` (`lib/tick/orquestar.ts#forzarRojoEnVecinos`): whenever a semáforo gets `anticipar_verde`/`extender_verde`, every geographic neighbor still without its own published decision gets a mechanically-synthesized `forzar_rojo_cruce` (new `AccionSemaforo` variant, added to `lib/tick/decision.ts` — deliberately outside the LLM's zod schema in `agent.ts`, so the model can never produce it itself, only the orchestrator). `faseEfectiva` treats it like the existing green-forcing actions: forced, `segundosRestantes: Infinity`, persists for the rest of the trip — same simplification already accepted for the green case, and harmless here too since the ambulance's own movement is never gated by semáforo state anyway (see the "ambulance is never slowed by traffic" invariant below). No extra LLM/TomTom cost: it's a direct `publicarDecision` call, gated by the same "only if the neighbor has no decision yet" check that already exists for the primary semáforo.
  - **Known false-positive risk, accepted rather than solved:** since the dataset has no real direction/street data, a semáforo 30-45m ahead on the ambulance's *own* path (not actually cross traffic) can get swept up as a "neighbor" and forced red too. Verified this doesn't break navigation — the ambulance's motion is never gated by semáforo state in this simulation (display/narrative only), so the only cost of a false positive is a momentarily-wrong badge on one marker, not a routing failure.
  - **Race condition, same class as the already-documented one below:** `publicarDecision` is a REST POST, `obtenerAccionesPrevias` reads from a separate WebSocket relay — no read-your-own-write guarantee. If a neighbor's own ETA *also* enters its decision window in the exact same tick (processed later in `orquestarTick`'s sequential loop), it may not yet see the freshly-published `forzar_rojo_cruce` and get its own independent LLM decision instead, permanently overriding the forced-red for that trip (since a semáforo only ever gets one published decision per trip). Not a new failure mode — it's the same Portal REST/WS propagation lag already documented for concurrent same-ambulance ticks (cost-audit section below), just newly reachable through this path too. Verified live against a real 4-node intersection cluster from the dataset (script run with real coordinates, fake-but-correct I/O deps): 1 semáforo green, 3 forced red, as expected.
- **Semáforo dataset (ticket #9) is real Overpass data, originally across 7 Lima districts, not the ticket's original 6-point table.** `lib/semaforo/semaforosSanBorjaYColindantes.ts` — real `highway=traffic_signals` nodes from San Borja + its 5 official neighbors (San Isidro, San Luis, La Victoria, Santiago de Surco, Surquillo) + Jesús María (not a San Borja neighbor, but where the fixed Rebagliati destination sits — without it, semáforos near the hospital itself are missing). Expanded beyond the ticket's original hand-picked 6 Javier Prado points at explicit user request, after discovering the real Mapbox route to Rebagliati doesn't stay on Javier Prado the whole way (it turns onto Petit Thouars a few blocks out), so a small fixed set tied to one street misses real coverage depending on which streets a given trip's route actually uses. `semaforoId` is the real OSM node id; `zona` is the district the Overpass query matched, not a cross-street label (labeling by transversal street name is still out of scope, same as the original ticket noted). Verified per-district via `relation[name=<distrito>][admin_level=8][boundary=administrative]` filtered by `pe:ubigeo` (several non-Peru relations share these district names) → `node(area)[highway=traffic_signals]`.
  - **Expanded to all of Lima Metropolitana (2026-08-08), replacing the 962-node/7-district set with 3784 nodes across 46 districts.** User already had a full-Lima Overpass extract downloaded (`docs/semaforos-osm.json`, ids prefixed `osm-`, plus `nombre`/`avenida`/`estado` fields that are uniform across all 3784 rows and carry no real information — `"Semáforo"`, `"Sin datos de vía (OpenStreetMap)"`, `"activo"`). Considered querying Overpass live at runtime instead of a bigger static file; rejected — Overpass has aggressive rate limits/timeouts and this data doesn't change, so a static seed stays strictly better regardless of dataset size, consistent with the original ticket #9 approach. Migration just strips the `osm-` prefix (to match the existing bare-numeric-id `semaforoId` convention already relied on elsewhere, e.g. `fase.ts`'s offset hash) and drops the three uniform/uninformative columns — same `SemaforoFijo` shape, same export name, no consumer changed. `semaforosEnRuta`'s corridor filter (see the rendering-freeze invariant above) already bounds what actually reaches the map regardless of source dataset size, so this is a pure data swap, not an architecture change.
- **Rendering the full semáforo dataset unconditionally freezes the browser — only render the active trip's filtered list.** Ticket #6's original invariant ("semáforos always blink, even with no active trip") assumed a dataset of 1. At ~1000 real signals, mounting that many Mapbox markers + `setInterval` timers at once hangs the tab (verified live while testing ticket #9). `components/SemaforosCorredor.tsx` now takes an explicit `semaforos` list — the current trip's `semaforosEnRuta(...)` output — instead of mapping the raw dataset; with no active trip, that list is empty and nothing renders.
- **`semaforos-ruta-1` (Portal channel) is the source of truth for interventions.** Reconstruct a semáforo's effective phase as: base deterministic cycle + any decisions already published to that channel for its `semaforoId` in the active trip. Don't build a separate mutable store for this.
- **Portal channel semantics differ by publisher and (since issue #12/#15) by scope:** `semaforos-ruta-1` (server, REST, **not** ephemeral — the server REST endpoint has no `ephemeral` field; this is accepted, not a bug) is still a single fixed channel shared by every ambulance, scoped by the `ambulanceId` field in each `DecisionSemaforoPublicada` (ticket #14). The ambulance position/route channels are **not** fixed anymore — see the slice #15 bullet below for the real-per-ambulance-channel pattern that replaced them.
- **The ambulance is never slowed by traffic.** It moves at Mapbox's estimated route-leg pace (priority vehicle). TomTom Traffic Flow (ticket #10, `lib/tomtom/trafficFlow.ts`, Flow Segment Data endpoint) is consulted only for cross-traffic congestion at each semáforo, as context fed to the LLM's decision — never to modulate the ambulance's own speed. **Queried at the semáforo's own coordinate, not a verified transversal-street geometry** — the semáforo dataset (ticket #9) never verified which street crosses at each node (explicitly out of scope), so TomTom's nearest-segment snap could return either the corridor or the cross street. Rate-limit handling (free tier: 2,500 req/day) is implicit, not a separate mechanism: the congestion lookup is gated behind the exact same "decide once per semáforo per trip" check as the LLM call (`orquestarTick`), so it's called at most once per semáforo per trip by construction. Failures (missing key, network, non-200) return `null`, not a thrown error — congestion is optional context, and losing it must never block a tick.
- **Destination is dynamic (issue #12, slice #13): nearest hospital by real route duration, not a fixed point.** `lib/hospital/hospitalMasCercano.ts` preselects candidates from `lib/hospital/hospitalesSanBorjaYColindantes.ts` by haversine, then asks Mapbox Directions (`driving` profile — the same route reused as `ambulanceRoute`, no duplicate fetch) for each candidate's real duration; lowest wins. **Does not exclude any hospital by specialty** — deliberate user decision, the opposite of what the issue's original text suggested (excluding pediatric-only). The old fixed point (Hospital Nacional Edgardo Rebagliati Martins) is just one row in the dataset now, not special-cased.
  - **Hospital dataset discovery, same Overpass approach as ticket #9's semáforos but a different OSM shape:** semáforos are always `highway=traffic_signals` *nodes*. Hospitals are not — `node[amenity=hospital]` across the same 7 districts returned only 4 results (small point-mapped clinics); neither Rebagliati nor the Instituto Nacional de Salud del Niño (the pediatric-only hospital that originally motivated issue #12) showed up, because real hospital complexes are mapped as *way*/*relation* polygons tagged `amenity=hospital`. Fixed by querying `nwr[amenity=hospital]` (node **and** way **and** relation) with `out center` to get a representative point for the polygon cases — 20 real hospitals across the same 7 districts. `hospitalId` is `"<osm-type>/<osm-id>"` (e.g. `"way/39413837"` for Rebagliati), not a bare numeric id like semáforos — the numeric id alone isn't unique across OSM types here.
  - Multi-ambulancia simulada, `/ambulance-watch` multi-instancia y la interfaz GPS pluggable son slices separados de la misma shaping de issue #12 — ver `docs/shaping/issue-12-destino-y-ambulancias.md` e issues #14–#16.
- **Múltiples ambulancias simuladas a la vez, cada una un trayecto independiente con `ambulanceId` (issue #12, slice #14).** `components/EmergencyMap.tsx` reemplaza los refs singulares (`ambulanceMarkerRef`/`ambulanceTimerRef`/`semaforosDeLaRutaRef`) por `Map<string, AmbulanceInstance>`. Un click normal en el mapa sigue funcionando exactamente igual que antes (resetea todo — "nueva emergencia"); el botón **"Agregar ambulancia"** arma un modo de un solo click que en cambio suma una instancia nueva sin tocar las existentes. `ambulanceId` (generado con `crypto.randomUUID()`) viaja en `RoutePublishPayload`, `AmbulancePositionPayload` y el body de `POST /api/tick` (`OrquestarTickInput`).
  - **Esto resuelve, como efecto colateral, el gap documentado desde ticket #7**: `obtenerAccionesPreviasSemaforo` (`lib/portal/serverReader.ts`) y `orquestarTick` (`lib/tick/orquestar.ts`) ahora escopan "ya decidido" por `(semaforoId, ambulanceId)`, no solo `semaforoId` — una decisión de un trayecto anterior, o de otra ambulancia activa a la vez, ya no bloquea una decisión nueva para el mismo semáforo físico. `DecisionSemaforoPublicada` (`lib/tick/decision.ts`) es la forma con `ambulanceId` que efectivamente se publica a `semaforos-ruta-1`; `DecisionSemaforo` (sin `ambulanceId`) sigue siendo lo que el LLM devuelve — no necesita saber para qué ambulancia está decidiendo.
  - **Límite conocido y aceptado, no un bug:** el mapa renderiza un marcador por `semaforoId` físico (unión deduplicada de los corredores de todas las instancias activas, ver `recalcularSemaforosVisibles`), así que si dos ambulancias distintas deciden para el mismo semáforo físico casi al mismo tiempo, el badge/popup solo puede mostrar la decisión que llegó más reciente — no ambas a la vez. La orquestación en sí sí es independiente por ambulancia; es un límite de tener un pin por ubicación en el mapa, no de la lógica de decisión.
- **Canal Portal real y separado por ambulancia, no compartido (issue #12, slice #15) — pivote explícito del usuario respecto a lo que el slice #14 había asumido.** `lib/portal/constants.ts#rutaAmbulanciaChannelId`/`ambulanciaChannelId` generan `ruta-ambulancia-<ambulanceId>`/`ambulancia-<ambulanceId>` en vez de los antiguos `ruta-ambulancia-1`/`ambulancia-1` fijos — el patrón que usaría un fleet-tracking real (una unidad, su propio topic, aislado de las demás). `AmbulanceInstance` (`components/EmergencyMap.tsx`) adquiere ambos canales al arrancar y los libera al detenerse; el campo `ambulanceId` se mantiene en los payloads de todos modos (autodescriptivo, redundante con el nombre del canal pero inofensivo).
  - **Problema de descubrimiento y su solución:** con canales dinámicos, un watcher no puede saber de antemano qué `ambulanceId` existen para suscribirse. Se agregó un canal fijo adicional, `PORTAL_AMBULANCIAS_ACTIVAS_CHANNEL_ID = "ambulancias-activas"` (cliente, una publicación por trayecto, no ephemeral — mismo carácter que `ruta-ambulancia-*`), donde cada ambulancia anuncia su propio id al arrancar. `/ambulance-watch` (`app/ambulance-watch/page.tsx`) se suscribe a ese canal para descubrir ids activos y renderiza un componente `AmbulanceRow` por cada uno — necesario porque las Rules of Hooks no permiten un número variable de llamadas a `useChannel` en un solo componente; un componente por fila, cada uno con su propia llamada, es el patrón correcto para N suscripciones dinámicas.
  - `semaforos-ruta-1` (decisiones semafóricas) **no** entra en este pivote — sigue siendo un canal único compartido, escopado por el campo `ambulanceId` del payload (ticket #14); ver la nota de esa línea arriba.
- **Ambulancia con posición GPS real, vía `POST /api/ambulance/[id]/position` (issue #12, slice #16) — mismo flujo que un click simulado, disparado por un device externo en vez de un click.** `PosicionSource` (`lib/mapbox/posicionSource.ts`) abstrae "de dónde viene la próxima posición": `InterpoladaPosicionSource` (timer local, reemplaza el `setInterval` que antes vivía directo en `EmergencyMap.tsx`) para las simuladas, `RealPosicionSource` (pasiva, reenvía lo que llegue por `ambulanciaChannelId(id)`, sin timer propio) para las reales. `AmbulanceInstance` ya no distingue el origen más allá de `detenerFuente()` — mismo shape para ambas.
  - **El endpoint corre en el servidor, no en el cliente que "creó" la ambulancia** — no hay tal cliente. En la primera posición de un `ambulanceId` nuevo, calcula el hospital más cercano (mismo `hospitalMasCercano` del slice #13) usando esa posición como origen, publica la ruta y anuncia el id en `ambulancias-activas` — igual que `iniciarAmbulancia` en el cliente, pero server-side. Los ticks (`orquestarTick`) también los dispara el propio endpoint (`lib/tick/deps.ts#crearOrquestarTickDepsReales`, factorizado y compartido con `/api/tick`) — un cliente que solo *observa* una ambulancia real (mapa principal, `/ambulance-watch`) nunca debe volver a llamar `/api/tick` para ella.
  - **Velocidad para el ETA se deriva de dos posiciones reales consecutivas** (`distance(anterior, actual) / (timestamp actual − timestamp anterior)`), a diferencia de una simulada (que ya conoce la ruta completa y su `durationSeconds`). La primera posición de cada `ambulanceId` no tiene "anterior" con qué calcular velocidad, así que ese primer POST no dispara `orquestarTick` — recién el segundo en adelante.
  - **"Llegó" se decide por distancia al destino** (`UMBRAL_LLEGADA_METROS = 50`, `app/api/ambulance/[id]/position/route.ts`), no por un campo que mande el device — coherente con que un GPS real no sabe cuál es "su" destino, ese cálculo es responsabilidad del servidor.
  - **Límite conocido, no implementado a propósito (documentado, no resuelto):** si una ambulancia real deja de mandar POSTs, no hay timeout ni remoción automática — ni del estado cacheado en el servidor (`__ambulanciasReales` en `globalThis`, igual patrón que el resto de `lib/portal/serverReader.ts`) ni del marker en un cliente que la esté observando (`RealPosicionSource` simplemente deja de emitir; el marker se congela en la última posición conocida, para siempre). No rompe el tick de otras ambulancias (cada una es independiente, sin loop compartido) — ver issue #16 para el criterio de aceptación que pidió documentar esto explícitamente.
  - **Hallazgo real de infraestructura, no de código:** `hospitalMasCercano`/`fetchDrivingRoute` nunca se habían llamado desde el servidor antes de este slice (siempre desde el click handler del navegador). El token `NEXT_PUBLIC_MAPBOX_TOKEN` tenía una restricción de Allowed URLs en el dashboard de Mapbox — el `fetch` del navegador manda un header `Origin` que la cumple; el `fetch` de Node desde el servidor no manda ninguno, así que Mapbox devolvía 403 `Forbidden`. Confirmado reproduciendo el 403 con `curl` y viendo que agregar `Origin: http://localhost:3000` lo resolvía a 200. El usuario quitó la restricción de URL en su dashboard de Mapbox para destrabarlo — si se vuelve a agregar una restricción de URL a este token en el futuro, cualquier llamada a Mapbox Directions desde el servidor (este endpoint) volverá a fallar con 403; en ese caso hace falta un token server-only sin esa restricción, no reintentar con el mismo.
  - **Reusa código server-side ya existente**, mismo patrón que "portal listen" (ticket #7): `lib/portal/serverReader.ts` se generalizó de "un canal fijo cacheado" (`obtenerCanalDecisiones`) a `obtenerCanalServidor<M>(channelId)` cacheado por id — necesario porque este endpoint necesita canales dinámicos por ambulancia (ruta, posición, y el registro) sobre la misma conexión WS de servidor, no solo el canal fijo de semáforos que ya existía.
  - **Bug real descubierto en vivo probando este slice, ya corregido:** `EmergencyMap.tsx` leía `.messages` de un canal justo cuando su `status` pasaba a `"ready"` y encontraba una lista vacía — el backfill de historial llega en un evento *posterior* separado, vía `subscribe()` (el "useSyncExternalStore-shaped store contract" del SDK), no junto con `"ready"`. Afectaba tanto el descubrimiento de ambulancias vía `ambulancias-activas` como la lectura de la ruta publicada de una ambulancia remota — en ambos casos, ninguna ambulancia ya anunciada antes de montar el mapa aparecía. Corregido re-suscribiendo (`esperarPrimerMensaje` en `EmergencyMap.tsx`) en vez de leer una sola vez tras `"ready"`.
- **Ambulancia simulada corre en el servidor, no en la pestaña que la creó (post-slice #16, bug real reportado por el usuario probando en producción).** Antes, `InterpoladaPosicionSource` vivía como un `setInterval` dentro de `EmergencyMap.tsx` — recargar o cerrar esa pestaña mataba el timer, así que cualquier otro observador (esa misma pestaña tras recargar, `/ambulance-watch`, otra pestaña) veía el marker congelado para siempre en su última posición, aunque el anuncio y la ruta seguían ahí. `lib/tick/simulacion.ts` mueve la simulación al servidor — mismo mecanismo que una ambulancia GPS real (slice #16): `iniciarSimulacionServidor` calcula hospital/ruta, publica ruta + anuncio, y corre `InterpoladaPosicionSource` (reusada tal cual, sin cambios — es puro TS, corre igual en Node que en el navegador) publicando posición y llamando `orquestarTick` en cada tick, sin importar qué pestañas estén abiertas. `POST /api/ambulance/[id]/simulate` la arranca; `EmergencyMap.tsx` ya no simula nada — el click handler solo hace ese `fetch` y luego observa la respuesta igual que a cualquier ambulancia (`observarAmbulancia`, la misma función que antes se llamaba `observarAmbulanciaRemota` — post-slice #16 ya no hay distinción real entre "local" y "remota", todo se observa igual).
  - **A pedido explícito del usuario: resetear el mapa (o cerrar/recargar la pestaña) también detiene, en el servidor, las simulaciones que ESA pestaña arrancó** (`DELETE /api/ambulance/[id]/simulate`) — no solo deja de observarlas. Sin esto quedarían corriendo para siempre, gastando cuota del LLM en cada tick. `misSimulacionesRef` (`EmergencyMap.tsx`) trackea qué ids arrancó cada pestaña, para distinguirlos de los meramente observados (creados por otra pestaña, o reales).
  - **Descubrimiento en vivo, mientras se implementaba este mismo fix: el cleanup de `useEffect` (`return () => {...}`) NO corre en una recarga dura ni al cerrar la pestaña.** React solo dispara ese cleanup cuando desmonta el componente por su cuenta (ej. una navegación SPA) — en una recarga real o al cerrar la pestaña, el navegador destruye el contexto de JS antes de que React tenga oportunidad de reaccionar; el `return` del efecto simplemente nunca se ejecuta. Confirmado en vivo: un primer intento que solo hacía el `fetch` de `DELETE` dentro del cleanup nunca llegó al servidor (verificado por logs), ni con un `navigate()` normal ni cerrando la pestaña. La forma correcta es un listener explícito de `window.addEventListener("pagehide", ...)` (más confiable que `beforeunload` con el bfcache) combinado con `fetch(..., { keepalive: true })` (para que el request siga en vuelo aunque la página ya se esté descargando) — confirmado con logs del servidor mostrando el `DELETE 200` inmediatamente después de una recarga real.
- **Tope de 8 ambulancias simuladas activas a la vez, a pedido del usuario.** `MAX_SIMULACIONES_ACTIVAS` (`lib/tick/simulacion.ts`) — chequeado contra `__simulacionesActivas.size` antes de gastar ninguna llamada real (Mapbox/LLM); una simulación sale del Map en cuanto llega a destino, así que el conteo siempre refleja las que siguen en ruta, no un total histórico. Solo cuenta simuladas, no ambulancias GPS reales (esas no tienen tope). Al llegar al tope, `iniciarSimulacionServidor` lanza `LimiteSimulacionesAlcanzadoError`, que la ruta HTTP (`app/api/ambulance/[id]/simulate/route.ts`) traduce a 429 (no el 502 genérico de otros fallos) con el mensaje real en el body — `EmergencyMap.tsx` lo lee y lo muestra tal cual, para ambas variantes de click (default y "Agregar ambulancia": antes del fix, `app/page.tsx` solo renderizaba el estado de ruta si `emergencyPoint` ya existía, así que un error del flujo "agregar" antes del primer click default nunca se veía).
- **Popup de decisión semafórica (ticket #11) con texto casi invisible en popups de mapbox-gl — bug real reportado por el usuario con screenshot.** `components/Semaforo.tsx#crearContenidoPopup` no fijaba `color` en el título/texto, así que heredaban el `color` de `body` (`app/globals.css`) — que en dark mode es `#ededed` (casi blanco) — sobre el fondo del popup de mapbox-gl, que **siempre** es blanco sin importar el tema del sistema. Texto casi blanco sobre fondo blanco. Corregido fijando colores oscuros explícitos (`#111827` título, `#374151` cuerpo), independientes del `prefers-color-scheme` del usuario.
- **Los markers de ambulancia se auto-remueven — a pedido del usuario, tras notar que el mapa acumulaba markers "fantasma" de ambulancias que ya no estaban activas.** Dos mecanismos, uno por cada causa real de que una ambulancia deje de moverse:
  - **Llegada natural**: `EmergencyMap.tsx#observarAmbulancia` ya recibe `arrived: true` en el propio stream de posición (ningún canal nuevo) — al verlo, programa un `setTimeout` de `TIEMPO_VISIBLE_TRAS_LLEGAR_MS` (4s, para que se vea "llegar") antes de quitar el marker.

Patrón a tener en cuenta para cualquier futuro `async`/`.then()` dentro de este mismo efecto que capture `map`/otras variables por-mount: `mountedRef.current` solo no alcanza si la espera es larga.

- **Portal auth is resolved (ticket #1).** Client: `NEXT_PUBLIC_PORTAL_API_KEY` (`pk_...`), passed to `new Portal({ apiKey })` from `@portalsdk/core`. Server: `PORTAL_SECRET` (`sk_...`), sent as `Authorization: Bearer <PORTAL_SECRET>` to `POST https://api.useportal.co/v1/channels/{channelId}/messages` — see `lib/portal/server.ts`, working end to end against the real API (round-trip verified at `/portal-test`). The `PORTAL_SECRET` name matches what `@portalsdk/cli` reads from the environment for its own admin operations (checked by inspecting that package's published source; it's not a project dependency here, so re-verify by fetching `@portalsdk/cli` from npm if this ever needs re-confirming). **Gotcha, undocumented anywhere, reproducible against the live API:** the secret-key REST publish requires an explicit `senderId` field in the body — the client SDK's typed publish path never needs this because it derives the sender from the connection's token, but a secret-key request has no session identity to derive one from. Omitting it fails with `{"code":"validation_failed","reason":"senderId is required"}` (this is a raw-REST behavior, not modeled in `@portalsdk/wire-protocol`'s client-oriented types).
- **Patched upstream SDK bug (ticket #5, `@portalsdk/core@0.1.5`, the latest published version): the client never dispatched incoming ephemeral messages.** Root cause, found by capturing raw WebSocket frames: the server relays another client's ephemeral send as its own standalone `{t:"ephemeral", userId, type, content}` frame — not wrapped in a `batch`/`direct` frame like every other message path. `@portalsdk/wire-protocol` never modeled this frame shape (no case in its validator; confirmed against `github.com/useportal/portal-sdk` main HEAD, so this isn't a stale-version issue), so `parseChannelFrame` classifies it as an `UnknownFrame` and the connection's `#onMessage` dispatch chain (`isChannelReady`/`isBatch`/`isDirect`/.../`isReassign`) silently drops it before `MessageBuffer.ingest()` — or any `message` event — is ever reached. (An earlier, now-reverted attempt patched `ingest()` itself on the theory that ephemeral `WireMessage`s arrived via `batch` and were filtered there; that was wrong — they never take that path at all, so that patch was dead code.)

  **Fixed via a local patch** (`bun patch @portalsdk/core`, tracked in `patches/@portalsdk%2Fcore@0.1.5.patch`, registered in `package.json`'s `patchedDependencies` so `bun install` reapplies it automatically): `#onMessage` now recognizes `{t:"ephemeral", userId, ...}` directly and synthesizes a public `Message` (id/timestamp aren't on the wire for this frame type, so they're generated client-side; `anon` is inferred from the `"anon_"` id prefix used elsewhere in the SDK, since the frame carries no explicit anon flag), then emits it exactly like any other `message` event — so `useChannel({ onMessage })` works as its own JSDoc always claimed. Verified end-to-end with two real browser tabs: the watch page's ambulance position now updates live across ticks.

  **This patch is fragile by nature** — it edits the installed package's minified `dist/index.js` and `dist/index.cjs` directly. Any `@portalsdk/core` version bump requires re-diffing `#onMessage` against the new dist output; the patch will silently stop applying (or worse, apply to different code) if the bundler's output shape changes. Re-verify this works after any `bun update @portalsdk/core`. Consider filing this upstream at `github.com/useportal/portal-sdk` so it's unnecessary in a future version.
- **Server-side Portal reads (ticket #7): the secret-key REST `GET /v1/channels/{id}/history` endpoint doesn't work.** It authenticates correctly (200, not 401/403 — confirmed by testing invalid/missing auth, which does 401) but **always returns `{"msgs":[],"hasMore":false}`**, even seconds after a successful secret-key POST to the same channel, on multiple different channels. This looks like a real gap in Portal's backend (not fixable client-side, unlike the ephemeral-dispatch bug above). **Working alternative, confirmed live:** connect server-side via the normal anonymous client protocol — same mechanism `@portalsdk/cli`'s `portal listen` command uses — by polyfilling `globalThis.WebSocket` with the `ws` npm package before constructing `new Portal({ apiKey: NEXT_PUBLIC_PORTAL_API_KEY })` (the *publishable* key, not the secret), then `portal.channel(id, { history: N }).acquire()` and read `.messages` once `status` reaches `"ready"`. Verified: a message published seconds earlier via secret-key REST POST showed up correctly in this WS-based read. See `lib/portal/serverReader.ts`. Because opening a fresh WebSocket per HTTP request is wasteful (and slow — connect + ready takes real time), the tick route keeps a module-scoped singleton connection, guarded against Next.js dev-mode HMR re-creating it on every edit.
- **Resolved (was "Known gap (ticket #7)"): "once per semáforo per trayecto" is now trip-scoped via `tramoId` (issue #20/#23).** Originally, no payload defined a `tripId`/`trayectoId` anywhere, so `lib/portal/serverReader.ts#obtenerAccionesPreviasSemaforo` and `faseEfectiva`'s reconstruction filtered `semaforos-ruta-1` by `semaforoId` alone — harmless while every `ambulanceId` was a fresh UUID per trip (a stale cross-trip collision was theoretically possible but practically rare), but the flota-persistente rework (issue #20) turned that into a guaranteed regression: a fleet unit reuses the same `ambulanceId` across every call it attends for its entire lifetime, so the second time it crossed a semáforo already decided on an earlier call, the decision would silently be skipped. - **`orquestarTick`'s per-semáforo loop is sequential, not parallel** (`lib/tick/orquestar.ts`, `await`s `obtenerAccionesPrevias`/`decidirAccion`/`publicarDecision` one semáforo at a time inside a `for` loop). With ~15–35 real semáforos per trip (ticket #9), a single pass can take longer than the 5s tick interval — this was originally logged as a benign "requests overlap in flight, but still complete correctly" limitation. **Cost audit (2026-08-08, skill `cost-audit`) found that assumption was wrong for the simulated-ambulance path**: overlapping `orquestarTick` invocations for the *same* `(semaforoId, ambulanceId)` genuinely double-decided semáforos — real data showed 31 LLM calls for 11 unique semáforos in one trip (64.5% pure reprocessing, confirmed via the new cost log below). Root cause: `lib/tick/simulacion.ts`'s position-tick callback did `void orquestarTick(...)` without waiting for the previous tick's call to finish, so a slow pass and the next 5s tick could run concurrently, each reading "no decision yet" for the same semáforo before the other's publish had propagated. **Fixed** with a `tickEnCurso` in-flight guard scoped per ambulance instance in `simulacion.ts`: a new tick skips (does not queue) triggering `orquestarTick` while the previous invocation for that ambulance is still running — position keeps publishing every 5s regardless, only the `orquestarTick` side effect is throttled. Validated live across 3 fresh trips post-fix: 17 calls for 16 unique semáforos (down to ~6% duplication, and that residual is attributable to Portal's own REST-publish→WS-relay propagation lag, a different and much smaller issue than the same-ambulance concurrency bug this fixes — see the log/endpoint below for future audits). **Not fixed for the GPS-real path** (`app/api/ambulance/[id]/position/route.ts` awaits `orquestarTick` per-request, so it's naturally serialized *unless* the external device posts overlapping requests without waiting for a response — untested, lower priority since device posting cadence is outside this repo's control). `Promise.all`-per-semáforo remains a separate, unrelated optimization opportunity for whoever next touches the loop's latency.
